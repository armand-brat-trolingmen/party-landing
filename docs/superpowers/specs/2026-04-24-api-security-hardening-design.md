# API Security Hardening Design

**Дата:** 24.04.2026

**Контекст:** проект уже имеет базовую валидацию формы, honeypot, timing-check, SmartCaptcha и запись в SQLite через prepared statements. При этом HTTP-периметр API остается слабым: нет allowlist-политики по origin, нет жесткого rate limiting на уровне middleware, а health endpoints не ограничены по частоте запросов.

## Цель

Усилить защиту backend API для формы заявок без поломки основного сценария сайта:

- принимать заявки только с доменов `party-everyday.ru`, `www.party-everyday.ru` и локальных dev-origin;
- не пропускать запросы с чужих origin до бизнес-логики;
- ограничить флуд и дешевые abuse-сценарии на уровне HTTP;
- ужесточить прием и нормализацию пользовательского payload;
- скрыть внутренние причины ошибок от клиента;
- подтвердить, что секреты не уходят в клиентский код.

## Не-цели

- не менять текущую модель доставки заявки в VK: одна заявка по-прежнему уходит во все настроенные `VK_DEFAULT_PEER_ID*`;
- не внедрять полноценную user-auth, сессии или кабинет;
- не строить WAF/anti-DDoS уровень CDN;
- не делать multi-node distributed rate limiting.

## Текущее состояние и реальные риски

### Уже есть

- `server/src/validation/leadValidation.ts` валидирует имя и телефон;
- `server/src/services/leadService.ts` имеет honeypot (`company`), timing-check (`form_started_at`) и SmartCaptcha-проверку;
- `server/src/db/leadsRepository.ts` использует prepared statements, поэтому прямой SQL injection в текущем write-path не является главным риском;
- наружу уже отдается общий текст ошибки без stack trace.

### Слабые места

- `POST /api/leads` сейчас не имеет allowlist-политики по `Origin`/`Referer`;
- текущий `rateLimit` мягкий: запрос доходит до API, а затем лишь помечается как spam-сигнал;
- нет отдельного rate limiting для health endpoints;
- нет централизованной CORS-политики для browser clients;
- нет явной периметровой защиты от oversized/musor payload;
- документация содержит лишние абсолютные локальные пути, что не является секретом, но является плохой гигиеной репозитория.

## Выбранный подход

Выбран вариант 2: нормальный баланс между безопасностью и риском поломки.

### Почему не только CORS

Один `CORS` не является достаточной защитой. Он ограничивает браузерный JavaScript, но не мешает `curl`, ботам и ручным POST-запросам. Поэтому защита строится в два слоя:

1. браузерный слой: CORS allowlist;
2. серверный слой: проверка `Origin` и fallback на `Referer` для state-changing запроса `POST /api/leads`.

## Целевое поведение

### 1. Allowed origins

Разрешенные origins:

- `https://party-everyday.ru`
- `https://www.party-everyday.ru`
- `http://localhost:*`
- `http://127.0.0.1:*`

Прочие origins не должны иметь доступ к `POST /api/leads`.

Для `POST /api/leads` вводится следующая логика:

- если `Origin` присутствует и входит в allowlist, запрос может идти дальше;
- если `Origin` присутствует и не входит в allowlist, сервер отвечает `403`;
- если `Origin` отсутствует, сервер пытается валидировать `Referer`;
- если и `Origin`, и `Referer` отсутствуют либо указывают на чужой origin, сервер отвечает `403`.

`GET /healthz` и `GET /api/healthz` не требуют origin-проверки, но попадают под rate limit.

### 2. Hard rate limiting

`POST /api/leads` должен ограничиваться на уровне middleware:

- лимит: `10 requests / minute / IP`;
- при превышении сервер сразу отвечает `429`;
- заявка не должна попадать в `leadService`, БД или VK.

Health endpoints:

- `GET /healthz`: `60 requests / minute / IP`;
- `GET /api/healthz`: `60 requests / minute / IP`.

Текущий мягкий флаг `softRateLimitExceeded` остается как дополнительный anti-spam сигнал внутри сервиса, но перестает быть единственной защитой.

### 3. Валидация и нормализация payload

Прием данных остается только по ожидаемой схеме формы и атрибуции.

Требования:

- имя и телефон остаются обязательными и валидируются строго;
- вспомогательные поля (`firstLeadSource`, `utm`, `referrer`, `userAgent`, `smartcaptcha_token`) нормализуются и режутся до безопасной длины;
- пользовательский input должен сохраняться и отправляться только как plain text;
- giant payload и мусорные типы должны отбраковываться рано;
- honeypot `company`, `form_started_at` и SmartCaptcha остаются частью антиспам-цепочки.

Важно: прямой SQL injection здесь уже снижен prepared statements. Основной смысл этой секции не "чинить SQLi любой ценой", а не принимать мусор, не расширять поверхность атаки и не тащить опасный input дальше по системе.

### 4. Error handling

Снаружи API должно отдавать только общие ответы:

- `400` для невалидной формы;
- `403` для запрещенного origin;
- `429` для rate limit;
- `500` для внутренних ошибок.

Во всех случаях клиент не должен видеть внутренние причины, конфиг, стек, SQL-ошибки, детали VK или SmartCaptcha.

Подробности остаются только в серверных логах.

### 5. Env and client-surface hygiene

Проверяется и сохраняется следующее правило:

- в клиент может уходить только публичный `VITE_SMARTCAPTCHA_SITE_KEY`;
- `VK_ACCESS_TOKEN`, `SMARTCAPTCHA_SERVER_KEY` и любые server-side env не должны попадать в browser bundle;
- конфигурация allowed origins должна быть управляемой, а не размазанной по хардкоду в нескольких middleware без явного центра.

## Изменения по слоям

### Backend app layer

Нужно добавить middleware/утилиты для:

- CORS allowlist;
- origin/referrer gate для `POST /api/leads`;
- hard rate limiting на `/api/leads` и health endpoints;
- унифицированных safe error responses.

### Service layer

Нужно сохранить текущую бизнес-логику anti-spam, но не полагаться на нее как на единственный барьер. Если hard limit или origin gate уже отклонили запрос, сервис не вызывается.

### Validation layer

Нужно усилить нормализацию и валидацию вспомогательных полей, не ломая текущий формат имени и телефона.

### Documentation layer

Нужно обновить deployment/docs так, чтобы там не было двусмысленности по allowed origins, rate limits и env-переменным, и убрать лишние абсолютные локальные пути из трекнутой документации там, где это уместно.

## Ограничения и честные компромиссы

- Проверка `Origin`/`Referer` не является криптографической аутентификацией frontend. Она режет стандартные браузерные сценарии с чужих доменов, но не заменяет полноценный CSRF/session/token-механизм.
- In-memory rate limiter защищает от дешевого abuse на одном инстансе, но не является распределенной защитой для multi-instance deployment.
- SmartCaptcha остается важной частью антиспам-цепочки, но не должна быть единственным барьером.

## Тестовая стратегия

Нужно добавить/обновить тесты на:

- разрешенный и запрещенный `Origin` для `POST /api/leads`;
- fallback на `Referer`, когда `Origin` отсутствует;
- hard `429` на `/api/leads`;
- hard `429` на `/healthz` и `/api/healthz`;
- отсутствие прохода в `leadService` при `403` и `429`;
- ужесточенную нормализацию и отбраковку мусорного payload;
- сохранение текущего поведения для валидной формы с разрешенного origin.

## Критерии готовности

- чужой origin получает `403` до бизнес-логики;
- флуд по `POST /api/leads` получает `429` до бизнес-логики;
- health endpoints ограничены по частоте;
- валидная форма с боевого домена и локальной разработки продолжает работать;
- секреты не утекают в клиент;
- клиент не получает внутренние причины ошибок;
- текущая VK-мульти-рассылка остается без изменений.
